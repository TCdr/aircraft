1. Independent CPT and F/O MCDUs

Aircraft: A32NX  |  Where: The two MCDUs on the pedestal  |  Status: Tested in the sim by the user: OK (2026-09-21): all 7 test points (pages, scratchpads, shared FMS data, per-screen messages, BRT/DIM, power).

What it is for

The two MCDUs mirrored each other: same page, same scratchpad. On the aircraft each MCDU is its own display, working on the shared FMGC data (A320 FCOM DSC-22_10-10). Now each pilot can work on a different page.

What is per MCDU and what is shared

Per MCDUShared (one FMS)
The page shown, the line keysThe flight plans, performance, fuel, navigation data
The scratchpad and what is typed in itThe data entered from either MCDU
The scratchpad messages (FORMAT ERROR, NOT ALLOWED ...) of an entryFMGC messages (queued on both)
The keyboard entry (the MCDU that was clicked)The EFIS symbols, the guidance

Messages

SituationWhat you should see
An entry is rejectedThe message shows on the MCDU where the entry was made.
An FMGC message (e.g. CHECK TAKE OFF DATA)Queued on both MCDUs; CLR on one clears it there only.
The FMS changes pages by itself (flight phase change on PROG / PERF / IDENT, engine-out page, INIT B to FUEL PRED)Applies to both MCDUs.
ATSU system status (not the answer to an entry)On the ATSU scratchpad of both MCDUs.
Typing with the PC keyboard (next feature)Goes to the MCDU that was clicked last; only that MCDU animates its keys.
SimBridge remote MCDU (next feature)CPT screen on its left side, F/O screen on its right side.

Power

  • CPT MCDU: AC ESS SHED bus. F/O MCDU: AC 2 bus.
  • An unpowered MCDU ignores its keys; the other one keeps working.

How it works

The FMS cannot be run twice: the MCDU code is the aircraft FMS (flight plan, guidance, EFIS symbols) as well as the display. So the two MCDUs are two screens on that one FMS, the way the A380X draws its two MFD screens: one 2048x1024 MCDU gauge, the CPT MCDU drawn in its left half and the F/O MCDU in its right half, and each screen of the cockpit model samples its own half. The F/O screen has its own copy of what belongs to a screen (page, line key actions, scratchpad, message queue, key handlers); everything else is the shared FMS.

Limitations and why

LimitationWhyWhat to do
No return to the MENU page after a power loss.Same as the CPT MCDU before this change.-

How to use

  1. Use each MCDU as on the aircraft: each pilot can open any page on his MCDU without changing the other one.
  2. Data entered on either MCDU (flight plan, INIT, PERF, fuel) is FMS data: it shows on both MCDUs.
  3. A scratchpad message (FORMAT ERROR, NOT ALLOWED...) shows on the MCDU where the entry was made; clear it there with CLR.
  4. An FMGC message is queued on both MCDUs: clear it with CLR on each MCDU.

2. Keyboard entry, SimBridge remote MCDU and ATSU status on both MCDUs

Aircraft: A32NX  |  Where: The MCDUs; flyPad > Settings > Realism; SimBridge remote MCDU  |  Status: Not sim-tested.

What it is for

After the split, three things still knew only the CPT MCDU: the PC keyboard entry, the SimBridge remote MCDU and the ATSU system messages. They now work with both MCDUs.

What you should see

SituationWhat you should see
Keyboard entry on, click on an MCDU screenThat MCDU gets the keyboard (cyan band at the top of its screen, highlighted scratchpad); the other MCDU loses it. Only one MCDU has the keyboard at a time.
Typing on the PC keyboardThe text goes into the scratchpad of the MCDU that has the keyboard; only the keys of that MCDU animate (before: both).
That MCDU is not poweredTyping does nothing (CPT MCDU: AC ESS SHED; F/O MCDU: AC 2).
A click outside both screensThe keyboard goes to the CPT MCDU, as before.
SimBridge remote MCDULeft side = CPT MCDU, right side = F/O MCDU (before: the CPT MCDU on both sides).
An ATSU system status that is not the answer to an entry (ATIS auto-update failure, a failed send from the mailbox, mailbox full)Shown on the ATSU scratchpad of both MCDUs (before: CPT only).
An ATSU status that answers an entry made on a pageShown on the MCDU of that page only.

Limitations and why

LimitationWhyWhat to do
An MCDU does not go back to the MENU page after a power loss.Neither MCDU did before (only the model blanks the screen); a reset could also cause nuisance resets on short bus transfers.-
The SimBridge remote MCDU needs SimBridge.It is an external program.Install and start SimBridge.

How to use

  1. Turn on flyPad > Settings > Realism > MCDU Keyboard Input (optionally set the MCDU Focus Timeout).
  2. Click the screen of the MCDU you want to type into, then type. Click it again (or press Alt) to give the keyboard back.
  3. For the remote MCDU, enable flyPad > Settings > Sim Options > Enable MCDU Server Connection and open the SimBridge remote MCDU.

How to test

#Do thisExpected result
1A32NX powered, both MCDUs on the MCDU MENU. Turn on flyPad > Settings > Realism > MCDU Keyboard Input.The setting is on; the focus timeout field appears.
2Click the F/O MCDU screen, then type ABC on the PC keyboard.The F/O MCDU top band turns cyan, ABC appears in the F/O scratchpad only, and only the F/O MCDU keys animate.
3Click the CPT MCDU screen and type 123.The keyboard moves to the CPT MCDU: 123 in the CPT scratchpad; the F/O MCDU loses its cyan band.
4Activate the flyPad failure ATA 24 > AC 2, click the F/O MCDU and type.Nothing is typed on the F/O MCDU.
5With SimBridge running: enable flyPad > Settings > Sim Options > Enable MCDU Server Connection, open the SimBridge remote MCDU, put the two MCDUs on different pages.The remote MCDU shows the CPT page on its left side and the F/O page on its right side.
6Optional (hard to trigger on purpose): make the ATSU report a system status, e.g. an ATIS auto-update that fails.The ATSU message appears on both MCDUs.

3. Close-up cockpit model: the MCDU screens in aircraft-large-files

Aircraft: A32NX  |  Where: Cockpit model, high detail (LOD00)  |  Status: The same 4 UV values were tested in the sim with the code above (2026-09-21); the large-files commit is byte-identical to the tested model. Pushed to the fork TCdr/aircraft-large-files 2026-09-29.

What it is for

The high-detail interior model A320_NEO_INTERIOR_LOD00, the one shown in the cockpit, is not in the aircraft repository: it lives in flybywiresim/aircraft-large-files. Its two MCDU screens (SCREEN_MCDUL, SCREEN_MCDUR) both sampled the whole MCDU texture. The companion commit 5563e31 (branch feat/a32nx-mcdu-screen-uv-split) maps each screen to one half:

MeshTexture U beforeTexture U after
SCREEN_MCDUL (CPT)0 .. 10 .. 0.5 (left half)
SCREEN_MCDUR (F/O)0 .. 10.5 .. 1 (right half)

Four float16 values change in A320_NEO_INTERIOR_LOD00.bin.part01, nothing else. This branch makes the same change to A320_NEO_INTERIOR_LOD01 (in the aircraft repository); the lower LODs have no MCDU screens.

Limitations and why

LimitationWhyWhat to do
Without the companion change, each MCDU screen shows both MCDU pictures side by side, squeezed.This branch draws the 2048x1024 two-screen texture; the large-files pointer of the branch still points to the unchanged model (5f07408).Merge the large-files change first, then bump the large-files submodule pointer on this branch.
The companion alone does nothing useful.With the stock 1024x1024 MCDU gauge, each screen would show half of the MCDU picture.Always install it with this branch.

How to use

  1. Merge the aircraft-large-files commit 5563e31, bump the large-files submodule pointer, then build the A32NX with this branch.
  2. Nothing to set in the cockpit.

How to test

2CPT MCDU: MCDU MENU > FMGC. F/O MCDU: stay on MCDU MENU.Two different pages.
3Type on one MCDU keypad.Only that MCDU scratchpad changes.
